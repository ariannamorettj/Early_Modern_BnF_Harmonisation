data.bnf.fr → harmonisation → research subset selection → research-ready CSV → knowledge graph → SAMPO portal

Six centuries of BnF records, put back in order

This pipeline takes every bibliographic record the Bibliothèque nationale de France has catalogued since the invention of print, cleans it field by field with rules earned from the data itself, cross-references people and editions against VIAF, Wikidata and the English Short Title Catalogue, and materialises the result as a linked open data knowledge graph built to the CHAD-AP application profile — not itself called "CHAD-AP": that name belongs to the profile the graph conforms to, not the graph. On top of it, a SAMPO-style discovery portal (module 08) is planned next.

·How it fits together

Nine modules, one direction

The repository is organised as a nested, numbered folder tree on purpose: the numbering is the execution order, and every module can be re-run on its own once its inputs exist. Data only ever flows downward — each stage reads the previous stage's output and writes its own.

00Cross-cutting

Monitor & test

Two utilities that run alongside every other module rather than before or after it: one watches resource usage while a script is working, the other proves the scripts still do what they claim.

monitor.py / monitor.R Checkpoint-based resource monitoring Aligned Python and R implementations. A script opens a monitor state, writes one checkpoint per meaningful unit of work (an actor, a batch, a distinct value), and closes it — CPU, memory, disk, GPU and network throughput land in a timestamped report.

Output the timestamped report below — one block per checkpoint, plus a final summary

04Python · Claude Opus 5

Harmonisation & evaluation

One normaliser per field. Every one of them follows the same order of operations, and the order is the point.

Exhaust cheap, deterministic, reproducible resolution before ever reaching for a model. A regex rule is free, instant, and exactly reproducible on re-run — a language-model call is none of those. The model only ever sees what the rule genuinely could not resolve.

Deterministic-first, LLM-as-last-resort — module 04's governing principle

Two fields turned out to need far less than their own documentation once assumed: language is a fully structured LOC vocabulary URI in the real data, and external links carry no free text at all — both are 100%-deterministic. Publisher is the opposite case: the messy free-text field the project expected, still partly resolved by a language model.

Every "before" value below is a real cell from the two module 01 tables — actor_name/actor_dates/external_links from actor_data.csv, publication_place/language/publisher from bnf_edition_data_raw.csv — not one is constructed for this page.

05Python

Subset optimisation

The actor table collapses from row-per-link-binding to row-per-person, gaining a compact map of which editions each person touched and in what role — and, on the way, can be scoped to a year range, so one research question doesn't have to pay the cost of processing every one of the 551,622 raw rows to get its answer.

Both scripts take --year-from/--year-to. A run with --year-to 1450 carves out editions published up to 1450 — a medieval-only sub-corpus for a specific research question — before the row-per-person collapse below ever runs; the numbers shown here are from a full, unfiltered run.

roles_enricher.py Role → editions map Scans the raw editions dataset and builds, per actor, which editions they touched in which bibliographic role. Takes the same year-range flags as the step below.

Input one actor URI, scanned across every edition row

Output a role_edition_map encoding role:id,id;role:id + a flat roles list

Input bnf_actors_ready.csv (module 04's ready-dataset output, above) + its role map

Output one bnf_actors_optimised.csv row — see the real example below

The ontology mix itself is real and current: CIDOC-CRM/LRMoo for bibliographic classes, the CHAD-AP obj: wrapper for actor-side properties — not Dublin Core or RDA, which this page previously (and wrongly) showed here.

Three YARRRML mapping files, one per CHAD-AP concern — actors, bibliographic entities, and the role arcs connecting them — are compiled by morph-kgc into up to three .nt shards and one merged graph. The roles shard only materialises when a role_edition_map column survives into the ready CSVs; on disk right now, only _actors.nt, _bibliographic.nt and the merged file exist for the sample profile — no _roles.nt yet.

The preprocess step picks its own upstream source automatically: module 06's enriched actors first, falling back to module 05's optimised actors if the enriched file isn't there; editions always come straight from module 04's bnf_editions_ready.csv, since there's no module-05 equivalent for editions to fall back through.

  1. scripts/bnf_graph_pipeline.py preprocess --profile full --force

    Input module 06's enriched CSVs (falling back to module 05/04, per above) Output ready CSVs, column-mapped to the YARRRML field names

  2. run_full_pipeline.py --profile full

    Input the ready CSVs + the three YARRRML mapping files Output materialise → validate → merge → report, all in one orchestrated run: knowledge-graph_actors.nt, _bibliographic.nt, _roles.nt (when present), _merged.nt

The orchestrator wraps four lower-level bnf_graph_pipeline.py subcommands (materialize, validate, merge, plus its own report step) — each still callable directly, one target at a time, for granular re-runs.
